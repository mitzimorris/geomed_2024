Spatial Data Analysis in Python and R

Overview

Areal data consists of a finite set of regions with well-defined boundaries. Geographic information systems (GIS) encode areal boundaries as a set of bounding polygons. To represent other features, e.g. area name and demographic together with GIS data we use packages which extend tabular dataframes to GIS data

  • Python: GeoPandas - add support for geographic data to pandas objects.
  • R: sf Simple Features for R - “spatial analysis simplified”

Region outlines - prefer low-resolution

Computing all neighbors for a map with many regions is computationally expensive; all polygons making up one region must be checked against all polygons of other regions for overlapping, shared, or very close boundaries or points. For this reason it is advisable to work with maps with a very coarse resolution as each area is described by fewer polygons, thus requiring less compute.

Neighbor graphs

By defining a neighbor relationship between area regions, we take the information from a GIS dataframe and convert it to a graph, where the areas are the nodes and edges denote the neighbor relationship. To compute neighbor graphs we use the following packages

  • Python: libpysal the Python Spatial Analysis Library Core
  • R: spdep Spatial Dependence: Weighting Schemes, Statistics

There are many ways to define contiguity, of these two straightforward metrics are Rook and Queen - regions which share bounding line are neighbors, and regions which share a bounding line or vertex are neighbors, respectively. The first sections this notebook show how to create, plot, and analyze spatial dataframes and neighbor graphs.

When geographic boundaries and conceptual boundaries don’t line up

Sometimes the contiguity graph doesn’t line up with the conceptual neighbor graph imposed according to some organizational schema. For example, the map may be drawn such that although a river separates one region from another, if the map is drawn such that they share a border somewhere at the bottom of the river. However if the river effectively prevents contact between inhabitants of the two regions, then for some analysis, they should not be considered neighbors and the graph must be modified accordingly. The later sections of this notebook show you how to do this.

Example Dataset: NYC traffic accidents, localized to US Census blocks

The dataset we’re using is that used in the analysis published in 2019 Bayesian Hierarchical Spatial Models: Implementing the Besag York Mollié Model in Stan.

The data consists of motor vehicle collisions in New York City, as recorded by the NYC Department of Transportation, between the years 2005-2014, restricted to collisions involving school age children 5-18 years of age as pedestrians.

Each crash was localized to the US Census tract in which it occurred, using boundaries from the 2010 United States Census, using the 2010 Census block map for New York City The US Census tract is the lowest level of Census data resolution. A tract contains between 2,500 and 8,000 residents and boundaries that follow visible features. According to the Census Bureau

When first established, census tracts are to be as homogeneous as possible with respect to population characteristics, economic status, and living condition

Measurements

We obtained motor vehicle collision data from the New York City Department of Transportation for the ten most recent years of data available at the time of request (2005-2014). Within this dataset, we identified collisions involving school age children 5-18 years of age as pedestrians. We then assigned each crash to the census tract in which it occurred, using boundaries from the 2010 United States Census.

We obtained 2010 US Census counts of youths aged 5-18 in each census tract from the US Census Bureau [@us-census] We also obtained the Census Bureau’s American Community Survey (ACS) five-year estimates of median household income and the percentage of commuters who traveled to work by means other than a private vehicle (i.e., by walking, bicycling, or using public transportation) for each tract for 2010-2014. We constructed an index of social fragmentation based on the work of Peter Congdon, using updated ACS estimates of vacant housing units, householders living alone, non-owner occupied housing units, and population having moved within the previous year. We standardized each of these metrics with a mean of zero and added them together as a single index. Finally, we obtained street level annual average daily traffic (AADT) data from the New York State Department of Transportation on the New York Open Data portal. We created a spatial overlay of streets and census tracts to assign each census tract the maximum AADT value of its underlying streets in 2015.

Spatial Data manipulation in R and Python

Geographic information systems (GIS) data is any item which has a geographic location, either a single point or a set of bounding polygons. Cartographic data (maps) are encoded as a set of records, one per map region. The shapefile format is an open specification used to insure interoperability among GIS software packages. When items in a dataset contain location labels, it is necessary to obtain a set of shapefiles for the corresponding map. To compute with GIS data, we need packages which can do the geographic math.

  • In Python the GeoPandas package extends the datatypes used by pandas to allow spatial operations on geometric types, and the libpysal package analyzes spatial relationships between locations.
  • In R the equivalent operations are provided by the sf and the spdep package.

To visualize GIS data, we need to be able to draw maps and spatial graphs.

  • In R, ggplot2 can produce beautiful maps for GIS data.
  • The python equivalent of R’s ggplot2 is plotnine. We also use the splot package which provides additional plotting functions for spatial graph networks.

From spatial dataframes to graphs

The neighbor graph is constructed from a geodataframe by analysis of the bounding polygons in the geometry column. Both libpysal and spdep provide functions to visualize neighbor graph overlaid on the map. The neighbor graph objects merely index entries in the geodataframe. Therefore plotting requires extracting the centroids of each regions from the geodataframe in order to align the graph to the map. Because the default indexing scheme is row index, it is critical that the dataframe and the neighbor graph remain in sync; reordering or otherwise modifying the geodataframe will completely scramble the graph and the resulting plot will look nothing like a proper network.

Connected and Disconnected Graphs: Components and Islands

A graph component is a set of 2 or more nodes for which there is a path from any node in the component to every other node in that set. A component is a set of nodes and edge pairs where every node is a member of at least one edge pair. A fully connected graph is a graph consisting of a single component, so that it is possible to find a path from any node in the graph to every other node. As the map of NYC shows (above), the graph is not fully connected, i.e., it is impossible to find a path from Staten Island to the Bronx, and there are 3 regions which have no neighbors - these are islands, (also called singleton nodes).

The libpysal and spdep APIs both provide a series of methods and attributes for computing properties of the neighbor graph.

Editing Neighbor Graph Objects

Oftentimes the geospatial structure obtained from the map boundaries may conflict with the logical spatial structure. Two regions may be map-wise adjacent but if the boundary between them is a river or road which prevents contact or mixing between the two regions, then they might not be considered “neighbors”. The converse is also problematic: the geo-coordinates of two regions may not share a bounding line or point but should be considered adjacent for the purposes of the analysis.

The NYC neighbor graph is problematic in both of these two ways. The first problem - map-wise adjacent but not logically adjacent - is that there are multiple edges between Manhattan, on one side of the East River, and Brooklyn, and Queens, on the other side. Perhaps this is due to administrative boundaries to account for bridges, tunnels, and subways, or else it could simply be a map artifact. For the analysis of pedestrian traffic, these regions should not be connected. The second problem arises if we want to use a single ICAR component to account for spatial variance which requires a fully connected neighbor graph.

To modify the graph so that it reflects the desired logical structure requires editing the libpysal W and spdep nb objects and to do this it is necessary to understand their respective APIs.

The libpysal W object API

This object contains 3 member dictionaries, plus several attributes. The key member variables are:

  • W.neighbors: A dict mapping each region ID to a list of neighboring region IDs.

  • W.weights: A dict mapping each region ID to a list of corresponding weights (aligned with neighbors). These quantify the strength of the relationship (often adjacency or proximity) between different geographic areas. Because the Rook metric computes a simple binary relationship, the value of all weights is \(1.0\).

  • W.cardinalities: A dict mapping each region ID to its number of neighbors.

If weights object is created without specifying the region IDS, (as we did above), the positional row indices of the geodataframe are used as ids.

Although the neighbors, weights and cardinalities dictionaries are mutable, the attribute n_components is computed on object instantiation, therefore after any edits to the neighbors and weights dicts, it is necessary to instantiate a new object using the edited neighbors and weights dictionaries. The cardinalities list will be recomputed, along with n_components and component_labels.

The spdep nb object API

The nb object only stores adjacency information; a separate listw object (e.g., spdep::nb2listw(nb, style = "W")) pairs an nb object with weights. The key components are:

  • nb[[i]]: A vector of integer indices for the neighbors of region i.
  • attr(nb, "region.id"): Character vector of unique IDs for each region.
  • attr(nb, "sym"): Logical indicating whether the neighbors list is symmetric (optional).

After editing a neighbor graph object, it is necessary to check that the edited object is both consistent and contains only valid node ids. At a minimum, you should check that

  • there are no duplicate neighbors
  • the weights are valid

Deleting edges from the neighbor graph

To delete an edge between nodes i and j in the libpysal W object requires updating the neighbors and weights entries for both i and j as well as decrementing the cardinality of each. If this edit disconnects the graph or subgraph, it is necessary to instantiate a new W object from the neighbors and weights list in order to recompute the n_components and component_labels attributes.

remove_symmetric_edge_nb <- function(nb, i, j) {
    nb[[i]] <- setdiff(nb[[i]], j)
    nb[[j]] <- setdiff(nb[[j]], i)
    return(nb)
}

Because these lists have 274 and 13,884 entries respectively, we use set operations for efficient computation, instead of repeated calls to remove_symmetric_edge.

clean_nbs_symmetric <- function(nb_obj, target_indices, remove_indices) {
  remove_set <- unique(remove_indices)
  for (node in target_indices) {
    original_neighbors <- nb_obj[[node]]
    neighbors_to_remove <- intersect(original_neighbors, remove_set)
    if (length(neighbors_to_remove) > 0) {
      nb_obj[[node]] <- setdiff(original_neighbors, neighbors_to_remove)
      
      for (neighbor in neighbors_to_remove) {
        neighbor_neighbors <- nb_obj[[neighbor]]
        nb_obj[[neighbor]] <- setdiff(neighbor_neighbors, node)
      }
    }
  }
  return(nb_obj)
}

Adding edges to the neighbor graph

To add an edge between nodes i and j in the libpysal W object requires updating the neighbors and weights entries for both i and j as well as incrementing the cardinality of each. If this edit changes the component structure of the neighbor graph you must instantiate a new W object from the neighbors and weights list.

In R, the nb object’s lists are sorted by node index, ascending, therefore after appending the i and j node index to the j and i entries, the list is re-sorted. Singleton nodes must be handled separately - instead of an empty list, singleton nodes have a list with the entry 0, which is an invalid node index, therefore we replace this entry with the node index of the new edge.

add_symmetric_edge_nb <- function(nb, i, j) {
  nb_res = nb             
  if (!(j %in% nb[[i]])) {
    if (nb[[i]][1] == 0) {
      nb_res[[i]] = j
    } else {
      nb_res[[i]] <- sort(c(nb[[i]], j))
    }
  }
  if (!(i %in% nb[[j]])) {
    if (nb[[j]][1] == 0) {
      nb_res[[j]] = i
     } else {
       nb_res[[j]] <- sort(c(nb[[j]], i))
     }
  }
  return(nb_res)
}

Example: New York City as single component

Going the other way, instead of removing connections between Manhattan and Brooklyn and Queens, we need to connect the other components and islands to the Manhattan / Brooklyn / Queens component. There are 4 additional components: the Bronx, Staten Island, the Rockaways, and Roosevelt Island, and three singleton nodes: City Island, Broad Channel, and Breezy Point.

Since the graph is not connected, there is no correct way to connect these regions, but we try to find reasonably “close” pairs of regions to connect.

To edit the libpysal neighbor graph and keep indices consistent between graph edits in R and Python, we define a helper function `add_symmetric_edge’.

add_symmetric_edge_nb <- function(nb, i, j) {
  nb_res = nb
  if (!(j %in% nb[[i]])) {
    if (nb[[i]][1] == 0) {
      nb_res[[i]] = j
    } else {
      nb_res[[i]] <- sort(c(nb[[i]], j))
    }
  }
  if (!(i %in% nb[[j]])) {
    if (nb[[j]][1] == 0) {
      nb_res[[j]] = i
     } else {
       nb_res[[j]] <- sort(c(nb[[j]], i))
     }
  }
  return(nb_res)
}

Comparison of packages libpysal and spdep

Both Python and R derive exactly the same neighbor graph from a geodataframe, however the packages differ in the internal structure and methods available for a libpysal W object and a spdep nb object.

Aspect libpysal.weights.W (Python) spdep::nb (R)
Data Structure Dictionaries (neighbors, weights, cardinalities) List of integer vectors
Adding Neighbors Append to lists and update weights/cardinalities Insert into sorted vectors
Disconnecting Neighbors Remove from neighbors, weights, and update cardinalities for both nodes Remove from neighbor lists and maintain sorted order for both nodes
Symmetry Handling Manually add or remove both directions Manually add or remove both directions
Weight Management Directly handled within the W object Typically managed separately (e.g., listw objects)
Sorted Neighbor Lists Not inherently sorted Maintained in sorted order
